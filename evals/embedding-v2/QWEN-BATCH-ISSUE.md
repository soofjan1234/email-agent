# Qwen3 在 TEI 1.9.3 CPU 中的批次一致性问题

## 结论

本次扩大数据集时发现，Qwen3 的部分相同输入会因为是否进入等长计算批次而输出明显不同的向量。已通过受控探针复现，并验证单输入串行规避有效。**原四输入配置下的 Qwen 分数仅作为故障证据，不用于模型优劣结论。**

这是运行配置规避，未修改或重新编译 TEI 源码。模型权重、输入前缀、数据和标签均未调整。最终四模型采用相同的单输入串行配置重新测量，参见[测试说明](README.md)。

## 现象与复现

环境为固定 TEI CPU 镜像 digest，实际版本 1.9.3、Qwen3-Embedding-0.6B 的固定 revision、float32、Candle CPU 后端。原 HTTP 输入批次和并发均为 4。

三轮完全相同的保留查询，Qwen 产品 Recall@3 分别为 92.86%、95.24%、90.48%，回复 Recall@3 为 90.48%、92.86%、88.10%。第二、三轮相对首轮有 9、2 条保留查询的 Top-3 排名变化；其他三个模型原配置三轮排名一致。原始数据见[异常实验汇总](reports/docker-2026-09-15/summary.json)。

为区分推理行为与标签问题，探针保持相同文本和角色前缀，比较单独输入、原顺序四条输入、逆序以及复制相同文本形成等长输入：

- `pd-nfs-root`：单独编码与重复两份的等长批次编码，余弦相似度约 **0.0371**；相同内容在普通非等长批次中可达到 1.000。
- `q-pd-nfs-subnet`：单独与原批次编码相似度约 **0.2736**，不能用正常浮点舍入解释。
- `pd-cache-read`：单独与原批次编码相似度约 **0.2208**。
- 向量长度、有限性和非零校验均通过，说明这些基本校验不能代替批次一致性检查。

[原始探针](reports/docker-2026-09-15/qwen-batch-probe.json)保留输入哈希、单独/批量向量、相似度矩阵和服务身份。

## 原因判断

实际对照排除了文本、标签、输入指令及权重版本变化，确认等长批量推理路径存在问题。现象与 [TEI 上游问题 #882](https://github.com/huggingface/text-embeddings-inference/issues/882) 相符：该问题描述 1.9.3 Candle 路径在等长输入不需要 padding 时可能遗漏 causal attention mask，改变模型计算。具体源码机制引用上游报告；本仓库验证的是实际端点行为，并未独立编译 Rust 测试。

## 规避与验证

首先尝试 `--max-batch-requests 1`，但此镜像的预热逻辑在运行时将它覆盖为 4。身份检查发现值不符并立即终止，未以此配置生成新质量结论。启动日志保存于[参数被覆盖的证据](reports/docker-2026-09-15/qwen-max-batch-requests-ignored.log)。

当前有效方式：

1. Compose 同时设置 `--max-client-batch-size 1`、`--max-concurrent-requests 1`。
2. Python 客户端每次发送一条，等待响应后再发送下一条；四模型统一使用此方式。
3. 验证 `/info` 的两个限额确实为 1，不能只检查启动命令。服务端内部报告的计算批次上限仍可能为 4，但请求接入限制避免多条同时进入。
4. 6 组探针对逻辑原序、逆序和重复输入均采用同一串行客户端方式，全部比较值在浮点精度内约为 1.000，并验证直接发送多输入批次会被拒绝。
5. 评测入口拒绝 TEI 1.9.3 Qwen 未采用已验证接入限额的服务，避免再次输出被该缺陷影响的比较分数。

[规避后探针](reports/docker-2026-09-15/qwen-batch-probe-fixed.json)与原始探针独立保存。[batch_probe.py](batch_probe.py)可复现实验；传参数 `1` 验证当前串行配置，传 `4` 仅复现异常。

## 历史证据与适用范围

此前 Docker v1 的 Qwen 指令/裸查询结果也使用该后端，不能再将其分数差异直接归因为提示词优劣：输入模板变化也可能改变等长合批。保留那些实际记录，但不把它们当作可靠选优结论。公司原服务是不同运行环境，不能自动把本次 TEI 缺陷外推到它。

单输入串行测试不验证并发生产吞吐。后续升级引擎或恢复批量请求时，应先重做单条、等长批次及顺序一致性验证，再重跑质量与性能；不能仅凭新版本号宣称问题已消失。
