# NAS 售后邮件回复 Agent 设计

## 1. 背景与当前事实

本项目面向海外 NAS 售后客服。第一版支持只读 IMAP 收件或本地样例，使用检索增强生成（RAG）查找相似历史案例和产品文档，由 Agent 生成英文回复草稿，再交给人工审核。审核通过后仅模拟发件并保存记录，不调用 SMTP，也不产生真实发件副作用。客户邮件、知识库、审核页面和模拟发件均为英文。

项目名称为 `email-agent`。仓库已实现 A1—A4 与 B1—B3 的后端代码，页面交付仍未开始；已确认的产品范围不包含工单能力。

## 2. 目标与非目标

### 2.1 目标

- 让只读 IMAP 增量和历史初始化中明确未回复的 NAS 售后邮件进入统一的 Agent 流程。
- 同时检索历史邮件与已审核回复、NAS 产品与排障文档。
- 基于可靠依据生成可编辑、可追溯的回复草稿。
- 知识不足、资料冲突或操作风险高时，不生成确定性的解决方案。
- 所有分类、优先级、风险判断和回复内容都由人工最终确认。
- 保存从收件、检索、生成、审核到模拟发件的完整审计记录。

### 2.2 非目标

- 第一版仅以只读 IMAP 读取真实邮箱，不实现 SMTP、OAuth 或供应商专用邮箱 API。
- 不发送真实邮件。
- 不创建或对接工单。
- 不处理保修、维修、退换货和物流。
- 不解析附件；样例邮件只包含主题和正文。
- 不支持多租户、多 Agent 或模型自主执行外部操作。
- 不以向量相似度或模型自报置信度代替人工判断。

## 3. 已确认的业务原则

1. 所有增量同步的新收件，以及历史初始化中明确 `unmatched` 的收件，都进入 Agent 流程；确定配对的历史邮件用于知识生产。
2. 第一版支持只读 IMAP 收件和模拟发件；真实发件留到后续版本。
3. RAG 使用两类知识：历史邮件与已审核回复提供表达样板，产品文档提供事实依据。
4. Agent 可以给出分类、优先级、风险、知识依据和回复草稿，但所有输出必须人工审核。
5. 超出知识库覆盖范围时，Agent 仍生成草稿，但只能说明依据不足、请求补充信息或建议人工处理。
6. 人工可以编辑草稿后批准，也可以拒绝。

## 4. 第一版业务范围

第一版支持的问题分类、优先级、风险边界、排除项和业务验收标准以 [MVP 范围与验收标准](README.md) 为准。本设计文档只说明这些业务要求的技术实现。

## 6. 运行时流程

### 6.1 日常邮件处理

```text
1. 用户触发“同步最新邮件”
2. 邮件同步服务调用邮箱适配器执行增量同步
3. 适配器按配置从只读 IMAP 或模拟历史邮箱读取；真实增量使用 UID 游标
4. 系统按外部邮件标识去重并保存，为邮件创建稳定的 Graph `thread_id`
5. 薄调度入口启动 LangGraph；Graph checkpoint 是 Agent 运行状态的唯一来源
6. Graph 规范化主题和正文并分类；垃圾邮件归档，VIP 投诉进入紧急人工路径
7. 普通邮件并行检索历史案例与产品文档，再评估检索相关性和证据充分性
8. 检索不相关时在次数上限内重写查询并再次检索；证据不足或高风险时生成信息请求或人工处理草稿
9. 证据充分时生成结构化分析和回复草稿，并校验输出契约、引用和风险约束
10. 生成校验失败时在次数上限内重新生成，超过上限后转人工
11. Graph 在人工审核节点调用 `interrupt()`，保存 checkpoint 并暂停
12. 人工批准、编辑后批准、拒绝或转人工；审核接口使用 `Command(resume=...)` 恢复同一 thread
13. 批准后幂等写入模拟发件箱，并创建唯一的候选案例
14. 每一步写入脱敏审计事件，邮件状态只作为列表查询投影
```

模型调用的临时错误按节点重试策略处理。检索改写和重新生成均有独立次数上限；输出无法解析、校验持续失败、低置信度分类或达到循环上限时进入人工路径，同时生成系统级失败说明。

### 6.2 历史邮件知识生产

```text
1. 程序启动时检查当前邮箱的历史初始化任务：首次创建，未完成则恢复，已完成则跳过
2. 后台任务固定初始化边界，全量拉取该边界内的历史收件和已发送邮件
3. 系统按外部邮件标识去重保存，并持久化扫描进度；不阻塞服务启动
4. 全量扫描完成后，根据邮件协议头建立完整关联关系
5. 仅将确定的一封收件与一封人工回复的一对一关系转为配对
6. 一对多、多对一、多对多、未匹配或关系不明确的邮件保留原文，记录暂不支持原因
7. 对确定的一对一配对清洗、脱敏并幂等生成候选案例
8. 人工复核配对关系、适用条件、事实来源和回复样板
9. 审核通过的候选案例完成切分与嵌入后，在同一事务发布为 active approved_case 并保存片段
```

MVP 不提供历史时间范围选择或手动回溯入口。初始化在后台执行，中断后从持久化进度继续；全部扫描与候选生成完成后才标记任务成功，服务重启不得重复生成邮件、配对或候选案例。多进程启动时，同一邮箱只允许一个初始化任务执行。

初始化边界用于区分历史数据与后续新邮件，不是用户选择的时间范围。初始化完成前不执行同一邮箱的增量同步；完成后从该边界继续拉取新增邮件。历史收件中明确没有对应人工发件的 `unmatched` 记录，在 B1 幂等创建为新邮件 Graph 的输入；已配对、复杂关联或解析异常记录仍只用于知识生产或保留待处理，不能因“未自动配对”而假定尚未回复。只有经人工复核并发布的案例才能进入 RAG。

### 6.3 邮箱适配器契约

邮箱适配器提供两种同步模式：

- `incremental`：初始化完成后，从持久化同步位置继续拉取新邮件；
- `historical_backfill`：由启动检查自动触发，在固定初始化边界内全量扫描收件和已发送邮件，不接收用户时间范围。

适配器必须支持稳定的初始化边界和可恢复扫描位置，确保初始化期间新增的邮件留给后续增量同步，既不漏收也不重复触发处理。

#### B1 真实 IMAP 增量约束

真实适配器以只读方式选择配置的收件文件夹，并将 `{uidvalidity, last_committed_uid}` 作为唯一有效的增量位置：`UID` 是文件夹内单调递增的永久标识，`Message-ID` 只用于去重，不能充当游标。历史初始化开始时读取 `UIDVALIDITY` 和 `UIDNEXT - 1`，将后者作为边界；初始化期间到达的更大 UID 由首次 B1 增量读取。每页邮件入库、`Email` 创建和游标推进在同一事务提交，未提交崩溃只会重读该页。

增量开始前必须比较当前与持久化的 `UIDVALIDITY`。若不一致，任务进入 `cursor_reset_required`，禁止静默推进或依据旧 UID 继续读取；恢复需要受控全量对账，并继续以外部邮件标识和内容哈希去重。真实历史“未回复”判定必须同时扫描显式配置的已发送文件夹，再根据 `In-Reply-To`、`References` 与 `Message-ID` 关联；IMAP 的 `\\Answered` 标记不作为业务事实。B1 不调用 SMTP，也不发送、移动、删除或标记任何真实邮件。

## 7. Agent 工作流状态

```text
START → classify_email
  ├→ spam → archive → END
  ├→ vip_complaint → urgent_manual_handling → END
  └→ retrieve_knowledge → assess_evidence
         ├→ rewrite_query → retrieve_knowledge
         ├→ information_request_draft ─┐
         ├→ manual_handling_draft ─────┤
         └→ solution_draft → validate_output
                    ↑             ├→ retry
                    └─────────────┘
                                      ↓
                              human_review interrupt
                                ├→ rejected/manual → END
                                └→ approved/edited
                                      → simulated_send
                                      → create_case_candidate → END
```

LangGraph PostgreSQL Checkpointer 唯一保存当前节点、Graph 状态、interrupt 和恢复点。`emails.status` 只保留 `received`、`in_progress`、`waiting_review`、`completed`、`failed` 等查询投影，不作为流程控制依据。审核接口必须校验当前 thread 的真实 interrupt；投影不一致时以 checkpoint 为准并执行对账修复。

Checkpoint 不是业务数据库。邮件原文、最终审核结论、模拟发件结果、知识和案例仍写入业务表；业务副作用使用唯一约束保持幂等。尚未完成 checkpoint 的节点可能在恢复时重放，因此任何副作用都不能只依赖“节点执行过一次”的假设。

## 9. 知识导入与检索设计

### 9.1 历史邮件配对与案例生产

历史导入的触发、恢复和增量边界统一遵循 6.2、6.3；知识生产流程为：

```text
首次启动全量导入历史收件和已发送邮件
  → 全量扫描完成后识别完整关联关系
  → 确定的一对一配对
  → 清洗、脱敏并提取问题、适用条件与回复样板
  → 人工复核
  → 完成切分与嵌入
  → 原子发布 active approved_case 及片段，供 RAG 使用
```

MVP 配对规则：

1. 使用 `In-Reply-To`、`References` 和 `Message-ID` 识别完整邮件关联；只有明确的一封收件与一封回复才能配对。
2. 必须先完成全量扫描，不能按局部批次提前确认一对一，不能从复杂会话中抽取一条边伪装成一对一。
3. 一对多、多对一、多对多、无确定协议头关系或未匹配邮件保留原文和暂不支持原因，不生成候选案例；复杂关系和模糊配对留到第二版。
4. 人工复核仅能确认或拒绝本版支持的确定一对一关系，不能绕过上述限制发布复杂会话。
5. 重试和服务重启不得生成重复邮件、配对或候选案例。

每次人工批准当前系统生成的草稿后，系统仍自动生成 `candidate`，但不直接写入活跃知识库。知识管理员需要再次检查事实来源、适用型号与版本、风险提示和脱敏结果，才能发布为 `active`。人工批准“本次可以回复”不等于该内容“可以复用于其他客户”。

案例状态流：

```text
candidate → reviewed → active
                     └→ rejected

active → archived
```

### 9.2 知识格式

第一版使用仓库内英文 Markdown 文件：

- 产品文档包含产品型号、系统版本、问题分类、事实说明、排查步骤、风险提示和来源。
- 已审核案例包含用户现象、适用条件、最终回复样板、人工修订说明和来源。

只有经过案例知识复核的内容可以标记为 `active` 并进入检索。人工本次审核产生的回复只创建 `candidate`，不会自动参与 RAG，避免错误自我强化。

#### 产品文档来源边界

当前 A3 的相对路径导入继续用于测试和开发环境中的固定 Markdown 夹具；它不是后续管理页面的文件上传契约。后续页面应提交 Markdown 文件内容，服务端生成稳定来源标识并在管理员身份边界内发布，生产默认关闭本地路径导入。双入口、版本冲突和安全边界见 `todo.md` 第 4 项；该上传能力尚未实现。

### 9.3 清洗与脱敏

- 删除签名、免责声明、重复引用链和无关转发头，同时保留原始记录用于审计。
- 脱敏邮箱、电话、地址、设备序列号、外网地址、账号和访问令牌。
- 脱敏后的占位符保留语义类型，例如 `[device serial]`、`[email]`，避免破坏案例结构。
- 清洗和脱敏结果必须在案例发布页面中与受控原文对照审核。

### 9.4 切分

- 按 Markdown 标题和语义段落切分，不使用固定字符数粗切。
- 每个片段保留文档标题、章节路径、产品型号、系统版本和来源类型。
- 单个片段过长时再按段落拆分，并保留少量相邻上下文。
- 文档内容哈希不变时跳过重复嵌入。

A3 使用实际模型 tokenizer，计入标题路径、文档前缀和特殊 token；超长段落按句界、空白、最后按字符边界递归拆分，每次都重新核对 token 数，不静默截断。代码围栏中的井号不作为章节。预算允许时保留同章节上一段末句；标题上下文本身超出预算则显式失败。长案例按用户现象、适用条件、回复和事实来源分章节，全部片段保留同一候选标识与文档版本，保持问答关联。

### 9.5 双路检索

1. 将邮件主题和正文作为查询生成向量。
2. 分别从 `product_doc` 和 `approved_case` 中检索，确保事实依据和表达样板不会互相挤占。
3. 每类同时执行全文检索和精确向量检索。
4. 使用 RRF 融合排名，去重后每类最多保留 3 条，总计最多 6 条。
5. 产品型号、系统版本只有明确提及时才作为过滤条件；未知时不猜测。

相似度分数只用于候选召回，不能直接决定知识是否充分。阈值必须通过固定评测集校准，不在设计阶段写死。

当前 A4 实现将关键词和向量候选按产品文档、已审核案例分开融合。返回结果只标记为“未评估依据”；后续 Graph 必须基于风险、适用条件、冲突和引用完整性确定 `knowledge_status`。案例可以提供表达和处理思路，但不能单独当作产品事实依据。

### 9.6 依据充分性

`knowledge_status` 取值：

- `sufficient`：检索事实能够支持关键结论，适用条件不冲突；
- `insufficient_information`：可能存在相关知识，但邮件缺少必要信息；
- `no_reliable_evidence`：没有可靠资料支持解决方案；
- `high_risk`：存在数据、安全或不可逆操作风险；
- `conflicting_evidence`：不同资料给出的结论不一致。

后四种状态禁止输出确定性解决步骤，只允许请求补充信息、说明风险或建议人工处理。

## 10. Agent 契约

Agent 返回严格 JSON，后端不接受 JSON 之外的自由文本：

```json
{
  "category": "storage_pool",
  "priority": "urgent",
  "risks": ["data_loss"],
  "knowledge_status": "high_risk",
  "reason": "The email describes a degraded storage pool; continued writes may increase data-loss risk.",
  "missing_information": ["device model", "DSM version", "storage pool status screenshot"],
  "citations": [
    {
      "chunk_id": "uuid",
      "usage": "fact"
    }
  ],
  "reply_draft": "Hello, the current information indicates a possible data-loss risk...",
  "requires_human_review": true
}
```

约束：

- `requires_human_review` 必须为 `true`。
- 引用的 `chunk_id` 必须来自本次检索结果。
- `sufficient` 以外的状态不得包含确定性的修复步骤。
- 回复中的型号、版本、命令和操作步骤必须能映射到产品文档引用。
- 历史案例只能提供措辞和处理思路，不能单独作为产品事实来源。
- 后端校验失败时不得进入人工审核 interrupt；应按循环上限重新生成或转人工处理。

## 11. API 契约

接口覆盖最新邮件增量同步、历史邮件回溯、邮件查询、人工审核、模拟发件、产品知识导入、历史邮件配对和候选案例发布。详细请求、响应、错误及幂等规则见[接口设计](architecture/api-design.md)。

## 12. 人工审核页面

审核页集中展示：

- 原始邮件；
- Agent 分类、优先级和风险建议；
- 知识充分性及原因；
- 产品文档事实引用；
- 历史案例样板引用；
- 可编辑回复草稿；
- 缺失信息和风险提示；
- 批准、编辑后批准、拒绝操作。

高风险、资料冲突或依据不足时，页面突出警告，但仍由人工决定最终动作。批准动作要求非空最终回复；拒绝和转人工要求填写原因。

## 13. 异步、幂等与错误处理

- 同一 Graph `thread_id` 的并发调用必须拒绝或串行化；重新处理邮件使用新的 workflow generation 或 `thread_id`。
- 模型调用设置超时；网络超时和服务端临时错误由节点重试策略处理。
- 查询改写和重新生成分别设置循环上限；达到上限、Prompt 注入风险或持续契约错误时进入人工处理。
- `client_request_id` 防止重复收件，`review_request_id` 防止重复审核，唯一 `review_id` 防止重复模拟发送。
- 邮件正文视为不可信数据，Prompt 明确将其作为待分析内容；正文中的指令不得改变系统规则、工具范围或引用要求。
- 人工审核记录使用 checkpoint/thread 标识防止重复恢复；业务写入使用明确事务，Graph 状态与查询投影最终一致。

## 14. 可观测性

### 14.1 日志

使用结构化日志记录：`request_id`、`email_id`、`graph_thread_id`、`checkpoint_id`、处理阶段、耗时、结果和错误类型。不记录模型密钥和完整邮件正文。

### 14.2 指标

- 收件数与各状态邮件数；
- 邮件端到端处理时长；
- 检索、嵌入和生成耗时；
- 模型与检索失败次数；
- 各知识充分性状态数量；
- 转人工比例；
- 草稿直接批准、编辑后批准和拒绝比例；
- 模拟发件幂等冲突次数。
- 历史邮件自动配对率、待人工确认率和错误配对率；
- 候选案例审核通过率及从候选到发布的耗时；

MVP 不引入分布式链路系统，但在日志和审计记录中贯穿同一 `request_id`、`email_id`、`graph_thread_id` 和 `checkpoint_id`，为后续接入 OpenTelemetry 留出字段。

## 15. 验证标准

业务验收场景和 MVP 完成标准以 [MVP 范围与验收标准](README.md) 为准。技术验证还需证明：

- Agent 引用的片段全部来自本次检索结果；
- checkpoint 能在 interrupt、进程重启和节点失败后恢复，且同一 thread 不会并发执行；
- 查询改写、补充检索和重新生成遵守循环上限，达到上限后进入人工路径；
- 重复审核恢复、节点重放和模拟发件不会产生重复业务记录；
- 模型超时、非法 JSON 和后端契约校验失败均能进入人工处理；
- 日志与审计记录可以通过 `request_id`、`email_id`、`graph_thread_id` 和 `checkpoint_id` 关联完整处理过程。
- 历史邮件优先通过协议头正确配对，歧义配对不会自动发布；
- 每次批准回复只产生候选案例，未经二次审核的案例不会进入检索；
- 案例发布、修改和归档都保留版本与审计记录；
- 清洗后的案例不泄露样例中的邮箱、电话、序列号、外网地址或访问凭据。

## 16. 已决策事项与剩余未知

### 16.1 已决策

- 领域：NAS 售后；
- 目标用户为海外售后；客户邮件、知识库、Agent 回复草稿、审核页面和模拟发件均为英文；
- 第一版模拟收件和发件；
- 不包含工单；
- 所有增量同步的新收件进入 Agent，历史初始化邮件仅用于知识生产；
- 所有 Agent 输出需要人工审核；
- 知识库同时包含产品文档和已审核历史案例；
- 人工可以编辑草稿；
- 知识不足时只生成说明不足或请求补充信息的草稿；
- 历史收件与人工回复经过配对、脱敏和二次审核后才能发布到知识库；
- 当前审核通过的回复只生成候选案例，不自动参与 RAG；
- 邮箱适配器统一支持最新邮件增量同步和启动时自动全量历史初始化；
- 第一版从模拟邮箱数据源主动拉取，第二版替换为真实邮箱适配器；
- LangGraph 是 Agent 工作流运行状态的唯一来源，使用 PostgreSQL Checkpointer、Conditional Edges、有限 Cycles 和 `interrupt()`；
- 人工中断不是单独采用 LangGraph 的充分理由，主要选型依据是高级 RAG 的非线性判断、回退和人工兜底；
- 具体技术选择以[技术选型](architecture/tech-design.md)为准。
- 第一版 Embedding 改为 [Docker 开放模型对比](designs/2026-09-13-embedding-truth-test-design.md)，原 API key 网关方案已废弃；新模型尚未冻结，历史 small 记录不作为新部署的建库依据。换模型必须新建索引版本，对已有数据全量重嵌入。

### 16.2 进入计划前的技术验证

模型、混合检索、英文关键词规范化、历史邮件配对、脱敏和任务可靠性的 truth test 统一记录在[技术选型](architecture/tech-design.md)。这些验证不阻塞业务设计成立，但应排在实施计划前部，未获得结果前不得固定模型、阈值和调优参数。
