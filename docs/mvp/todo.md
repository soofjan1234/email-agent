  2. A4.11 未覆盖指还没有专门代码和测试的三类：
- 输入长度：现在没有明确上限。例如有人提交几十万字的问题，系统可能仍把它送去向量模型，带来耗时、超时或成本问题。
- 恶意查询：还没专门验证大量重复字符、控制字符、极端标点组合等异常输入是否会造成异常耗时或不可预期行为。这里不是说已经存在漏洞，而是尚未证明安全。
- 限流：没有验证“同一个人一分钟只能查多少次”。如果有人高频请求，每次都会触发向量模型和数据库检索，可能挤占正常用户资源

3. A4.12 还没证明的是：
- 大语料性能：例如 100 万片段时，数据库是否仍选择 GIN 索引、一次查询要多久。
- P95：100 次查询中，最慢的那 5 次通常多慢；这是用户实际体验的关键指标。
- 索引膨胀：文档反复新增、更新、归档后，GIN 索引会不会变得很大、很碎，导致磁盘和查询性能恶化。

5. LangGraph 节点不按“每个函数一个节点”机械拆分，而按需要独立决策、重试、持久化、恢复、等待外部事件、执行不可逆副作用或独立观测的边界划分：
- 有明确输入和输出：例如“邮件正文 → 分类结果”“检索结果 → 证据结论”。
- 有条件分支：例如高风险邮件直接转人工，普通邮件继续检索。
- 有重试或循环：例如证据不足时改写查询后回到检索；草稿校验失败后重新生成。
- 需要独立持久化和恢复：例如检索或生成已经完成，服务重启后不应重新执行此前成功的步骤。
- 需要等待外部事件：例如人工审核、异步任务结果或审批结果。
- 有不可逆副作用：例如发送邮件、创建工单、调用外部写接口；这类节点必须具备幂等保护。
- 需要独立观测：例如单独统计检索耗时、模型调用失败率、命中率或成本。

纯粹的轻量数据整理通常不必单独成节点，例如格式化 Prompt、拼接文本、字段默认值处理和将检索结果转换为模型输入。

邮件 Agent 后续可按“分类与风险判断 → 检索 → 证据评估 →（依据不足时）查询改写并回到检索 → 草稿生成 → 草稿校验 → 人工审核 interrupt → 审核后幂等副作用”拆分。当前实现只有 `process_email` 和 `await_review` 两个显式节点：前者包含多个可重试但尚未独立持久化的步骤，后者负责人工暂停。后续是否拆细，应以恢复粒度、可观测性和流程复杂度为依据，而不是为了图看起来更细。
