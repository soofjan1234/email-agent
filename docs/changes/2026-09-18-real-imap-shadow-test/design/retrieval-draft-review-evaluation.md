# 检索、草稿与人工审核评估设计

## 目标

在不读取更多 IMAP 邮件、不真实发信、不把合成邮件表述成真实客户结论的前提下，完成三类可复算评估：

1. 用 32 封真实未回复邮件和 508 封 synthetic v2 待回复邮件验证关键词全文检索、向量检索和 RRF 混合检索的效果与耗时，并按来源拆分结果。
2. 量化从未回复邮件到“可人工审核草稿”的端到端 P50/P95，并定位最耗时步骤；真实样本与 synthetic v2 容量样本分别报告。
3. 汇总人工对草稿的直接批准、编辑后批准、拒绝和转人工比例，以及编辑成本。

本设计不是上线 SLA、真实发信测试、盲测或真实售后问题占比统计。

## 当前基础与范围

- 真实 IMAP 可见范围内已有 243 个源邮件；其中 32 个明确未配对 Inbox 邮件已进入隔离库的业务邮件流程，12 个确定收发配对仅作为待审核历史候选。
- 知识库已有 3 份官方产品资料摘要、12 个有效片段；这只证明导入链路可用，覆盖面不足以得出检索效果结论。
- 已完成的 `imap-shadow-20260918-synthetic-v1` 保持为“只做历史配对和候选”的审计基线，不修改、不重跑，也不进入工作流。
- 后续新建 `imap-shadow-20260918-synthetic-v2`，仍保留 2,057 个合成源邮件规模和 711 组确定配对；635 个无回复 Inbox 改为 127 个垃圾邮件与 508 个待回复售后邮件。
- 所有评估读取既有隔离数据库，报告只输出脱敏 ID、数量、耗时、模型/提示词身份、文档/片段标识、Codex 初标和人工抽检结果，不导出邮件正文、地址或凭据。
- 不审核或发布历史配对候选，不把其人工回复放入评估语料；本轮检索语料只有官方 `product_doc`。

## 一、先扩充并冻结产品资料集

### 覆盖目标

以现有 3 份总览资料为基础，补充到总计 8–12 份针对性官方资料。每份文档只回答一个主要支持主题，至少覆盖：

| 主题 | 文档要点 |
| --- | --- |
| LincOS 下载与升级 | 型号识别、官方下载入口、版本核对、升级前后安全检查 |
| 服务管理与 Docker | 服务状态、容器功能入口、数据保护边界 |
| E1 安装与网络访问 | 硬件安装、首次连接、Web UI/客户端与远程访问排查路径 |
| S1 启动与系统恢复 | 启动页异常、重置、恢复或重建前的备份边界 |
| 数据迁移 | 源盘/目标盘/容量/备份的前置检查 |
| N1/N2 SSD 与 NVMe | 盘位、未识别、状态与关机后物理检查 |
| 风扇、温度与触控配件 | 风扇设置、温度记录、触控屏或触控笔基础排查 |
| 型号选择与兼容性 | E1、N1、N2、S1 的适用场景与客户端支持路径 |

每份资料必须保存官方 URL、抓取日期、适用型号和摘要；不得复制长段落、用户评论或客户邮件。资料完成后固定以下评估身份：文档 SHA-256、文档数、片段数、分块器版本、Embedding 模型/revision/维度和索引版本。评估期间不得修改资料集。

### 分块规则

继续使用现有 Markdown 分块器：保留标题路径和段落，只有超过 Embedding 服务实际报告的 token 上限时才按句子或字符兜底拆分。不得按固定字符数强制切分原始邮件；原始 `MailMessage` 仅用于审计和输入，不直接成为知识片段。

## 二、检索基准

### 输入、Codex 初标与人工抽检

- 输入集：现有 32 封真实未回复业务邮件，加上 synthetic v2 的 508 封待回复售后邮件；合计 540 封。每条只在隔离数据库内读取，报告以稳定的脱敏样本 ID 表示，并记录 `sample_source=real|synthetic_v2`。
- 纳入条件：正文可解析、非垃圾邮件、非高风险/注入路径、包含可由产品资料回答的支持问题。
- 排除样本必须记录排除原因；排除后剩余数量是本轮评估分母。检索相关性、草稿质量和审核结果同时输出总评估集结果及两个来源的拆分结果。
- Codex 对每个纳入样本的每个检索通道的 Top-3 产品资料片段批量初标：`relevant`、`partially_relevant`、`not_relevant`，并允许标记 `no_answer`。初标必须保存 `judge_model`、Prompt 版本、`judge_run_id`、候选片段 ID、标签、置信度和简短依据。
- 提交给 Codex 的三个候选片段必须去除检索通道名称并随机排列，结果由稳定 ID 映射回原始名次；因此 Codex 只判断“资料是否能回答邮件问题”，不因关键词、向量或 RRF 名称产生偏向。
- 人工不做全量标注，只抽检所有低置信度和 `no_answer` 结果，并从其余结果按真实/合成来源、检索通道和四类标签分层随机抽取 10%。抽检记录 `confirmed`、`corrected` 或 `unable_to_judge`，并保留更正后的标签。

检索正确率以 Codex 初标计算，但报告必须显式标为“Codex 判定”；同时给出人工抽检量、与 Codex 的一致率和更正后指标。若未完成规定抽检，只能报告查询成功率、返回数量和耗时，不能将 Codex 初标表述为已校准的检索正确率。

### 对比口径

对同一冻结资料集、同一查询文本、同一 metadata 过滤和同一 Top-K=3，分别执行：

1. 关键词全文检索。
2. 向量检索。
3. 当前固定参数的 RRF 混合检索。

不得在三种通道间改变分块、文档、查询改写、Top-K 或筛选条件。查询改写在本基准中关闭；如后续单独评估改写，必须建立新的评估组。

### 输出指标

| 维度 | 指标 |
| --- | --- |
| 规模 | 样本数、排除数、文档数、片段数、总 token 数、Embedding 身份 |
| 效果 | Recall@1、Recall@3、MRR@3、`no_answer` 误命中率、无依据片段率 |
| 稳定性 | 成功数、失败数、超时数、空结果数 |
| 性能 | 每种检索的 P50/P95/最大耗时；向量编码、关键词查询、向量查询、RRF 融合分别计时 |

本轮不预设“通过 P95 阈值”。先得到稳定基线，再由业务目标决定后续性能目标。

## 三、synthetic v2 的垃圾分流与待回复流程

### 运行边界

synthetic v2 使用独立 mailbox ID、独立本地 `.eml` 目录和独立历史任务，不覆盖 v1 或真实 IMAP 的任何记录。加载历史任务后，只有 v2 的 635 个明确未回复 Inbox 允许进入后续业务流程；711 组已配对邮件继续仅作为历史候选，不参与草稿生成。

| 无回复类型 | 数量 | 预期流程 | 不允许的行为 |
| --- | ---: | --- | --- |
| 垃圾邮件 | 127 | 投影后由现有安全预检识别并归档 | 不检索、不调用 Generator、不创建审核任务、不发送 |
| 待回复售后邮件 | 508 | 投影后进入检索、草稿生成、输出校验和待人工审核状态 | 不自动批准、不调用 SMTP、不写入真实 mailbox |

垃圾邮件模板必须能触发现有垃圾邮件分流规则；验收时分别记录 127 个归档结果及其零检索/零生成次数。508 个待回复邮件必须保留原有 65/35 主题比例，并且只在产品资料集冻结后才批量进入草稿链路。

synthetic v2 的 508 封待回复邮件进入检索相关性、草稿质量和人工审核统计，与 32 封真实邮件共同构成总评估集。所有报告必须同时给出总评估集及按 `sample_source` 拆分的结果；不得把 synthetic v2 的结果表述为真实客户邮件效果或真实售后问题占比。

## 四、草稿端到端 P95

### 前置条件与运行方式

检索基准完成且人工确认资料覆盖后，固定知识库、Generator 模型/版本、Prompt 版本、运行环境和并发度。真实样本与 synthetic v2 分两组运行；草稿 P50/P95 同时输出总评估集和按来源拆分的结果：

1. 真实功能组：每个纳入的真实未回复邮件运行 10 次；第一次只作预热，不计入 P50/P95。若纳入样本为 32 个，统计样本量为 288 次正式运行。
2. synthetic v2 容量组：127 个垃圾邮件各运行一次，验证分流；508 个待回复邮件在预热后各运行一次，形成 508 次草稿链路样本。若需要重复压测，必须创建新的 `evaluation_run_id`，不得覆盖首次结果。

所有运行只创建待审核草稿，不调用 SMTP，也不自动批准。

### 分段计时

每次运行记录同一 `evaluation_run_id` 下的下列 span：

1. 邮件读取、分类和风险预检。
2. 查询向量编码。
3. 关键词检索、向量检索与 RRF 融合。
4. 查询改写及其额外检索（如发生，单独记录次数）。
5. Generator 调用。
6. 输出校验、引用校验和安全降级。
7. 草稿/审核任务持久化。

报告总时延的 P50/P95/最大值，以及每个 span 的 P50/P95、失败数与重试数。瓶颈定义为同一固定配置下，对总耗时贡献最高的可测步骤；不能把多个步骤各自的 P95 相加后当作单次端到端 P95。

## 五、人工审核结果

### 统计分母

以一个 `graph_thread_id + checkpoint_id` 的最终 `Review` 记录为一个审核单位。审核集包含 32 封真实邮件和 508 封 synthetic v2 待回复邮件；每项比例同时输出总评估集及按 `sample_source` 拆分的数值。当前模型已保存以下终态动作：`approve`、`edit_and_approve`、`reject`、`manual_review`。

| 指标 | 公式 |
| --- | --- |
| 直接批准率 | `approve / 完成审核数` |
| 编辑后批准率 | `edit_and_approve / 完成审核数` |
| 拒绝率 | `reject / 完成审核数` |
| 转人工率 | `manual_review / 完成审核数` |
| 总可接受率 | `(approve + edit_and_approve) / 完成审核数` |
| 免编辑批准率 | `approve / 完成审核数` |

待审核、运行失败、被归档和没有最终 `Review` 的邮件不进入分母，但必须单独计数。四类终态比例之和必须为 100%。

### 编辑成本与原因

`edit_and_approve` 使用已保存的 `original_draft` 与 `final_content` 计算字符数、token 数和编辑距离的 P50/P95。拒绝或转人工的原因分布不能从自由文本猜测；若需要统计原因，后续应新增受控原因码，例如 `missing_evidence`、`wrong_product_scope`、`unsafe_instruction`、`customer_context_missing`、`policy_escalation`。

## 数据、审计与安全边界

- 每次基准创建不可变 `evaluation_run_id`，绑定样本 ID 集合、资料集哈希、检索参数、模型身份、Prompt 版本、运行时间和代码版本。
- 单次运行失败、超时、无产品依据、输出校验失败都保留为独立结果，不能从 P95 或审核分母中静默删除。
- 报告不输出原始邮件、草稿正文、地址、凭据或客户身份；需要人工核对时仅在受控隔离库中查看。
- synthetic v1 只能用于已完成的历史加载审计；synthetic v2 的 127 封垃圾邮件只用于分流验证，508 封待回复邮件可进入受控检索、草稿和人工审核评估。总评估结果必须标注来源构成，synthetic v2 不得被表述为真实检索质量、真实草稿业务质量、真实审核率或真实问题统计。
- Codex 只承担检索相关性初标和受控草稿质量辅助判断；`approve`、`edit_and_approve`、`reject`、`manual_review` 仍是人工对最终草稿作出的终态动作，Codex 不得批准或发送邮件。

## 验收标准

1. 冻结的官方资料集共有 8–12 份针对性文档，所有主题都有官方来源和明确适用范围。
2. 三种检索通道在同一固定样本、资料集、Top-K 和 metadata 条件下，对 32 封真实邮件与 508 封 synthetic v2 待回复邮件输出可复算结果；Codex 初标、来源拆分、排除原因和规定的人工抽检齐全，并报告抽检一致率与更正后指标。
3. synthetic v2 的 127 个垃圾邮件均归档且检索/生成次数为 0；508 个待回复邮件均到达待审核或有可追溯失败原因，真实网络发信次数为 0。
4. 草稿测试报告给出 540 封总评估集以及真实功能组、synthetic v2 容量组的 P50/P95、各 span P50/P95、失败/重试数和确定的瓶颈步骤；报告明确各来源样本数，不能把总评估值表述为真实邮件值。
5. 审核报告按最终 `Review.action` 计算四类比例，并给出总评估集与按来源拆分的数值；待审核数量独立列出；若统计原因，全部来源于受控原因码。

## 未决项与后续关卡

- 这份设计确认后，下一步应写实施计划：资料补充顺序、Codex 标注 Prompt 与结果结构、抽检模板、评估表结构、span 埋点、报告脚本和回归测试。
- 在人工确认前，不新增审核原因码、不执行批量草稿、不修改生产数据结构或 API。
